# 招呼语模板版本埋点与 HR 回复归因规则（v2.1 任务三）

> 状态：**本周只定规则，不实现回复抓取**。本文档是后续实现回复关联时的唯一依据。

## 1. 模板版本埋点（已实现）

### 1.1 三风格变体

`boss_apply.generate_greeting_with_meta()` 按 JD 关键词匹配角色（Agent/AI应用/RPA/采购/测试…），
再按公司名确定性轮换三种风格：

| 模板 id | 风格 | pattern 要点 |
|---------|------|--------------|
| `T1:<角色>` | 技术栈对齐型 | 直接以角色背景开场 + 角色专属追问 |
| `T2:<角色>` | 业务场景型 | 追问岗位负责的业务场景 |
| `T3:<角色>` | 项目亮点型 | 以独立交付项目亮点开场 |

素材约束：自我介绍段（bg）一律取自 `USER_BG` 用户真实背景，问句取自 `ROLE_QUESTIONS`
角色词表，**绝不编造经历**。

### 1.2 确定性轮换

```
style = md5(company_name_utf8) % 3   # pick_greeting_style()
```

- 不用内建 `hash()`——str 哈希受 `PYTHONHASHSEED` 随机化，跨进程不稳定；
- 同一公司+岗位重跑必得同一 `(招呼语, template_id)`，保证落库可复现；
- 落库位置：`applications_v2.greeting_template_id`（如 `T2:AI应用`）。

## 2. HR 回复归因规则（只定规则，暂不实现）

### 2.1 输入定义

- **回复事件**：会话维度的一条 HR 来信（含公司名、会话标题/岗位名、时间戳）。
- **投递记录**：`applications_v2` 中 `decision IN ('applied','uncertain')` 的记录
  （跳过/失败的没有会话，无从归属）。

### 2.2 关联算法（按优先级依次尝试，命中即止）

设回复事件携带的公司名为 `reply_co`，候选投递记录的公司为 `app.company`：

1. **精确匹配优先**：`app.company == reply_co`（原串完全相等，含大小写敏感的原始名）
   → 候选集 A。
2. **归一化包含匹配兜底**：对两边先做归一化（去城市前缀/括号后缀/空白/中点，
   转小写，复用 `store.normalize_company()`），再要求
   `norm(reply_co)` 与 `norm(app.company)` 之间满足**一方包含另一方**
   → 候选集 B。
3. **时间窗约束**：只考虑 `applied_at <= 回复时间` 且回复时间在投递后 N 天内
   （N 默认 14，可调）。避免把历史会话错挂到新投递上。

### 2.3 歧义处理——宁缺毋滥（硬规则）

- **同公司多岗**：候选集内命中多条不同 `title` 的投递 → **全部丢弃，不硬凑**。
  只有当会话标题/岗位名能唯一对应到一条投递的 title 时才允许归属。
- **匹配不上**：候选集为空 → 丢弃该回复事件，计入"未归因回复"统计，
  绝不强行塞给最近一次投递。
- 归因结果只允许两种：`唯一命中（写入 replied=1 及关联 application_id）` 或
  `不归属（仅留在未归因池）`。不存在"大概率算它"的中间态。

### 2.4 为什么这么严

归因错误的代价高于漏归因：把 B 公司的回复记到 A 头上会直接污染
"招呼语模板 → HR 回复率" 的 A/B 结论。漏掉的样本只是少一个数据点，
错配的样本是反向噪声。因此规则设计为一票否决制。

### 2.5 实现边界（本周不做）

- 不抓取会话列表、不读取 HR 回复内容；
- 不新增任何网络请求路径；
- 后续实现时入口建议放在 report/followup 链路旁路，只读
  `applications_v2.greeting_template_id` 与新会话数据做离线关联。
